# Protocols & Wire Format Reference

This document describes how `AIStudio2API` handles Google AI Studio's internal MakerSuite protocol, translates public API requests, and decodes streaming wire formats.

---

## 1. MakerSuite JSON+Protobuf Wire Format

Google AI Studio's web client communicates with Google servers using a JSON serialization of Protocol Buffers (`application/json+protobuf`).

### Array Indexing Rule
- Protobuf message fields are **1-indexed** (`field 1`, `field 2`, ...).
- JSON arrays representing these messages are **0-indexed** (`index 0`, `index 1`, ...).
- **Fundamental Rule**: `Protobuf Field N` is stored at `JSON Array Index N - 1`.

*Example*: If a protobuf definition specifies `string prompt = 1` and `int32 timeout = 5`, the JSON wire format is `["hello", null, null, null, 30]`.

### Sparse Arrays & Null Normalization
Google servers often omit empty slots or return sparse JSON arrays with trailing or omitted commas (e.g. `[,value]`). The decoder in `internal/aistudio/decoder.go` normalizes missing and omitted slots into explicit `null` elements before traversing message structures.

## 2. GenerateContent Request Wire Layout

`GenerateContent` requests are serialized as a top-level array in `internal/aistudio/generate.go`:

| Array Index | Protobuf Field | Content | Notes |
|---|---|---|---|
| `0` | Field 1 | Contents Array | `[[parts, role], [parts, role], ...]` |
| `1` | Field 2 | System Instruction | System prompt text wrapped in a canonical message block |
| `2` | Field 3 | Safety Settings | Standard safety threshold settings (must be `null` for image generation models) |
| `3` | Field 4 | Generation Config | Temperature, topP, topK, maxOutputTokens, thinking config, image/speech config |
| `4` | Field 5 | WAA Proof | Cryptographic attestation proof generated by Camoufox (`!xxxx`) |
| `6` | Field 7 | Tools & Capabilities | Function declarations, Google Search, Code Execution, or output resolution slots |
| `10` | Field 11 | Version Marker | Fixed integer `1` |
| `13` | Field 14 | Tool Config | Tool configuration (e.g. `include_server_side_tool_invocations: true`) |

## 3. Function Calls & Tool Results

### Function Call Part Representation
In the canonical wire structure:
- **Function Call Part**: Represented as a 3-element array: `[name, StructArguments, callID?]`.
- **Function Result Part**: Represented with the result object in slot 11: `[name, StructResult, callID?]`.

### Tool Result Correlation Rules
Client tool results in multi-turn conversations must be correlated back to previous assistant tool calls:
1. **Explicit Name**: If the tool result provides a function name, it is preserved.
2. **Call ID Match**: If name is omitted, the proxy correlates the result with pending function calls from the current turn using `call_id`.
3. **Single Uncorrelated Call**: If an uncorrelated call remains, its name is inferred.
4. **Fallback Safety**: If correlation is completely impossible due to malformed client history, the proxy emits `unknown_function` to avoid throwing a fatal 400 error that breaks the conversation.

## 4. Thinking & Thought Signatures

### Wire Placement
- The thought signature is stored at index `14` (protobuf field 15) of an individual content Part:
  ```go
  func setPartThoughtSignature(wire []any, signature string) []any {
      for len(wire) <= 14 {
          wire = append(wire, nil)
      }
      wire[14] = signature
      return wire
  }
  ```
- Thought signatures received from upstream **must be echoed back** in subsequent conversation turns to maintain reasoning context.

### Anthropic Thinking Mapping
- **Adaptive Thinking**: When Anthropic clients send `{type: "adaptive"}`, the proxy lets the model use its default reasoning configuration.
- **Budget to Level Mapping**: For models supporting only discrete thinking levels (minimal, low, medium, high), token budgets are mapped:
  - Budget $\le 0$ $\rightarrow$ minimal (level 4)
  - Budget $\le 1024$ $\rightarrow$ low (level 1)
  - Budget $\le 8192$ $\rightarrow$ medium (level 2)
  - Budget $> 8192$ $\rightarrow$ high (level 3)

## 5. Image & Video Model Wire Constraints

Image generation models (`gemini-3-pro-image`, `gemini-3.1-flash-image`, `gemini-2.5-flash-image`) have strict protocol constraints:
1. **Modality**: `responseModalities` **must** be `[IMAGE, TEXT]`. Requesting `IMAGE` alone results in `403 Code 7`.
2. **Safety Settings**: Wire slot `2` (`safetySettings`) **must be null**. Sending proxy safety settings triggers `403 Code 7`.
3. **Output Resolution**: Models with `output_resolution` capability require wire slot `6` set to `[[null,null,null,[null,[[]]]]]` and `imageConfig` default `[null, "1K"]`.
4. **Extension Header**: Header `X-Goog-Ext-519733851-Bin` must be cleared for image generation requests.

## 6. Event Streaming Architecture

Upstream sends chunked responses via WebDriver BiDi or HTTP streaming. The decoder translates these chunks into canonical events:

```go
type EventKind string

const (
    EventText               EventKind = "text"
    EventReasoning          EventKind = "reasoning"
    EventToolCall           EventKind = "tool_call"
    EventExecutableCode     EventKind = "executable_code"
    EventCodeExecutionResult EventKind = "code_execution_result"
    EventMedia              EventKind = "media"
    EventUsage              EventKind = "usage"
    EventFinish             EventKind = "finish"
    EventThoughtSignature   EventKind = "thought_signature"
)
```

Each adapter in `internal/api/` translates these events into the protocol's expected format (e.g. OpenAI `chat.completion.chunk` SSE, Anthropic `content_block_delta` SSE, or Gemini streaming JSON).
